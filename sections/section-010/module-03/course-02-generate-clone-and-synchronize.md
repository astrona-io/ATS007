# Part 2 — Generate: Clone & Synchronize

> Prerequisite: [Part 1 — Mutate: patchStrategicMerge & patchesJson6902](./course-01-mutate-patchstrategicmerge-and-json6902.md). Next: [Section 020 — YAML Manifests](../../section-020/README.md).

Mutate rules edit the resource that triggered them. Sometimes what you actually need is a *different, brand-new* resource to appear as a side effect — a default `NetworkPolicy` the moment a `Namespace` is created, or a shared `ConfigMap` copied into every new namespace without asking anyone to remember to do it. That is what `generate` rules are for.

## Generation creates separate resources

A `generate` rule does not touch the resource that triggered it. It watches for a trigger — most commonly a new `Namespace` — and creates a *different* resource in response: a default `NetworkPolicy`, a `ResourceQuota`, a copy of a shared ConfigMap. The trigger resource itself is admitted unchanged.

Because generation reacts to cluster events rather than to an inbound admission request, it is driven by the background controller, not the admission controller. That is also why a generated resource can appear a moment after its trigger rather than atomically with it.

## Generating from an inline definition

The simplest form writes the new resource's spec directly inside the policy:

```yaml
generate:
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  name: default-deny-all
  namespace: "{{request.object.metadata.name}}"
  synchronize: true
  data:
    spec:
      podSelector: {}
      policyTypes:
        - Ingress
        - Egress
```

Triggered on `Namespace` creation (via `match`), this creates a `default-deny-all` `NetworkPolicy` inside the newly created namespace — `{{request.object.metadata.name}}` resolves to that namespace's own name at generation time.

## Generating with `clone`

Instead of writing the resource's contents inline, `clone` copies an existing resource that already lives somewhere in the cluster — the standard pattern for propagating a shared Secret, ConfigMap, or PullSecret into every namespace without maintaining N copies of the same content by hand:

```yaml
generate:
  apiVersion: v1
  kind: ConfigMap
  name: shared-settings
  namespace: "{{request.object.metadata.name}}"
  synchronize: true
  clone:
    namespace: platform
    name: shared-settings
```

Here, the source of truth is the `shared-settings` ConfigMap living in the `platform` namespace; every new namespace gets its own copy, generated by Kyverno rather than a script someone has to remember to run. The playground ships a source object of exactly this shape so you can see what a clone rule would be copying.

> [!TIP]
> **Try it — inspect the clone source**
>
> ```sh
> kubectl -n platform-config get configmap cluster-defaults -o yaml | head -15
> ```
>
> Expect something like:
>
> ```text
> apiVersion: v1
> data:
>   log-level: info
>   region: eu-west-1
>   telemetry-endpoint: otel-collector.platform-config.svc:4317
> kind: ConfigMap
> metadata:
>   name: cluster-defaults
>   namespace: platform-config
> ```
>
> Three keys in one namespace. A `generate` rule with `clone` pointed at this object is what turns it into a copy in every namespace created from then on — the source stays where it is, and the copies are separate resources with their own lifecycle.

## `synchronize`: what stays in sync, and with what

`generate.synchronize` controls what happens *after* the initial generation:

- **`synchronize: false`** — the resource is generated once. Edits to the generated copy, or to the source it was cloned from, are never propagated again. It's a one-time scaffold.
- **`synchronize: true`** — Kyverno continuously reconciles the generated resource to match its source (for `clone`) or its policy definition (for an inline `data` block). If someone manually edits the generated copy, Kyverno reverts the drift. If the source resource (or the policy itself) is deleted, the generated copies are deleted too.

Neither is universally right. Synchronised generation gives you a guarantee; unsynchronised generation gives namespace owners room to adapt what they were handed.

> [!WARNING]
> **Common pitfalls**
>
> - **Setting `synchronize: true` on something owners are meant to customise.** A generated `ResourceQuota` that some teams need larger than the default will have every local edit silently reverted on the next reconciliation pass. That reversion is the feature working as designed, not a bug — but it means `synchronize: true` belongs on cluster-wide invariants you never want drifted from, and `synchronize: false` on one-time starting points owners are expected to adjust.
> - **Forgetting that deleting the policy deletes synchronised copies.** Under `synchronize: true`, removing the generate rule — or its source resource — removes what it generated. Cleaning up a policy can therefore remove `NetworkPolicy` or `ConfigMap` objects that live workloads depend on.
> - **Expecting a generated resource to appear instantly.** Generation is driven by the background controller reacting to a cluster event, not by the admission request itself. A brief gap between the trigger being created and the generated resource existing is normal.

> *A generate rule's output is a separate object with its own lifecycle — and `synchronize` decides whether that lifecycle belongs to the policy or to whoever edits it next.*

## Reference

- `kubectl explain clusterpolicy.spec.rules.generate` — the live schema for `clone`, `cloneList`, and `synchronize` on your installed version.
- `kubectl get networkpolicy,configmap -A` — a quick way to confirm generated resources actually landed where a generate rule intended.
